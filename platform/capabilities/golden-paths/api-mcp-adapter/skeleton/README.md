# ${{ values.name }} — Remote REST-to-MCP adapter

${{ values.description }}

This repository was generated by the platform's API-to-MCP Golden Path.
It publishes **a private Streamable HTTP MCP endpoint** in Kubernetes, inside
the same ephemeral namespace as the existing REST backend:

- Environment: `env-${{ values.environment }}`
- Business API: `${{ values.backendService }}` (already deployed)
- Remote MCP: `${{ values.name }}` (new Deployment + ClusterIP Service)
- Internal REST destination: `http://${{ values.backendService }}:80`

The MCP is not a database client, does not generate SQL, and is not public.

## 1. Configure reviewed business tools

Replace the sample `operations.json` (which exposes only `/api/health`) with
explicitly approved read-only GET paths from your backend API contract.
**For Retail Sales Insights**, use the matching `retail-operations.json` from
`examples/scenarios/example/data/` in the Starter Kit.

The four Retail operations are: `sales_summary`, `top_products`,
`sales_by_category`, `compare_sales_periods`.

## 2. Test and deliver

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -e '.[test]'
pytest -q
git add operations.json
git commit -m "Expose reviewed Retail read-only queries"
git push origin main
```

The generated Gitea Actions pipeline then tests the contract, builds and
pushes a **multi-architecture** Python OCI image, writes it into
`deploy/mcp.yaml`, and Argo CD deploys to `env-${{ values.environment }}`.

The template deliberately starts with an empty image reference, so the first
GitOps sync becomes healthy only after the pipeline successfully publishes it.

To verify:

```bash
kubectl -n env-${{ values.environment }} rollout status deployment/${{ values.name }} --timeout=180s
kubectl -n env-${{ values.environment }} get svc/${{ values.name }}
kubectl -n env-${{ values.environment }} get pods -l app.kubernetes.io/name=${{ values.name }}
```

If the rollout fails, inspect the Gitea delivery pipeline and Argo CD
Application `${{ values.name }}`. The platform runner requires Python pip
and venv: deploy the updated platform runner before the initial build.

## 3. Connect Claude Code from ANY folder

**Terminal 1** — keep the tunnel open:

```bash
kubectl -n env-${{ values.environment }} port-forward svc/${{ values.name }} 18081:8080
```

**Terminal 2**, opened in any arbitrary directory:

```bash
claude mcp add --scope user --transport http ${{ values.name }} http://127.0.0.1:18081/mcp
claude mcp list
claude
```

Inside Claude Code, use `/mcp` to check the connection, then ask:
"Which business operations can you query?" or "What were the retail sales
between November 16 and 22, 2026?" (if the Retail allowlist is configured).

The `user` scope applies across Claude Code working directories. A different
person on another laptop must run their **own port-forward** and their own
`claude mcp add` command, using an individually authorized Kubernetes account.
`127.0.0.1` always refers to that person's laptop, not the presenter's.

If `claude mcp add` reports a duplicate server name, remove the old user
registration and add it again. The tunnel must remain running during use.

## Local stdio fallback

You can still use the same source locally:

```bash
MCP_TRANSPORT=stdio REST_API_BASE_URL=http://127.0.0.1:18080 \
  .venv/bin/rest-mcp-adapter
```

For that fallback, expose the **backend** separately with `kubectl
port-forward svc/${{ values.backendService }} 18080:80`. This is not the remote
MCP workflow.

## Security scope

No public ingress, no direct database access, no arbitrary SQL/HTTP paths.
`operations.json` permits only reviewed GET calls with typed parameters.
Inside Kubernetes, plaintext HTTP is allowed **only** to the declared business
service and only when actually running in a Kubernetes pod.

**Port-forward access is controlled by Kubernetes identity/RBAC, not by MCP
tool-level OAuth.** Do not share kubeconfig. Production requires stronger
identity, policy and network boundaries.
